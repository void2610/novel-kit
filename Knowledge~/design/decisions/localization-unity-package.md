# 状況

[ローカライズ v1 ADR](/design/decisions/localization.md) は「日本語のみ + 抽出フック」で確定し、
`ITextResolver`（既定は恒等変換）が say 本文・話者表示名・choose 選択肢に適用済み
（[API 表面](/design/api-surface.md)）。多言語は「このフックの差し替えで非破壊後付け」と約束されている。
本 ADR はその後付けの具体方策である。

前提と制約:

- **著者体験（`.rb` にプロセ直書き）は変えない**（v1 ADR の核心）。シナリオライターがキーの羅列を
  書く方式は最初から論外で、`.rb` 上のテキストは常に読める日本語プロセであること。
- 原文は書き直されるもの（誤字修正・推敲・タグ付け足し）。**原文が変わっても訳が迷子にならない
  追従機構**が方式の成立条件である。これが無い原文キーは「一度書いたら直せない」制約を著者に課す
  ことになり、v1 の核心と矛盾する。
- `Novel.Runtime` は純 C# を維持し、特定のローカライズパッケージへ直接依存しない。
  未導入の game には一切の負担を掛けない（opt-in）。
- 運用前提: **ライターの原稿はエンジニアレビュー付きの PR で取り込まれる**。原稿ファイルに
  ツールが入れる注釈は、エンジニアがレビューで意味を担保できる（2026-08-07 議論で確認）。
- 既存プロジェクト群には Unity Localization Package (`com.unity.localization`) の採用実績がある
  （Locale 管理・CSV/Google Sheets 連携等のツーリング資産）。ただしこれは**バックエンド候補の参考**で
  あって前提ではない。コア契約はバックエンド中立に設計し、Unity Localization は第一実装とする。

# 決定

方策の核は 3 点: **(a) 原文キー**（著者はプロセを書くだけ）、**(b) 追従抽出パイプライン**
（原文変更を差分検出してキーリネームに変換し訳を運ぶ）、**(c) opt-in resolver**
（`ITextResolver` 差し替え・コア API 不変）。テーブルバックエンドは中立で、
第一実装として `Novel.Localization`（Unity Localization 統合）を同梱する。

## 1. キー戦略: 原文（日本語 raw テキスト）をそのままキーにする

- `.rb` は日本語直書きのまま。String Table のキーに **resolve 前の原文**（インラインタグ込み、
  `SayCommand.Text` / `DisplayAs` / カタログ表示名 / choose 選択肢の生文字列）を使う。
- resolver は `Resolve(raw)` で raw をキーに現在ロケールのテーブルを引き、
  **ヒットしなければ raw をそのまま返す**（テーブル未整備・訳抜けでも従来挙動に落ちる健全なフォールバック）。
- 日本語ロケールはキー自体が表示文字列なのでテーブル値は不要（入れてもよい）。
- `ITextResolver` のシグネチャは不変。既存 seam をそのまま使い、コア API に変更は生じない。

```
say "本気なの？"                     # .rb は不変（著者体験そのまま）
   └ ITextResolver.Resolve("本気なの？")
        └ StringTable[ja→そのまま / en→"Are you serious?"]  ヒットしなければ原文
```

- タグ込み原文がキーになるため、**翻訳文も同じインラインタグを訳側で書く**
  （`<w>`/`<color>` 等の位置は言語ごとに移動してよい）。タグ整合の検証はバックログ（後述）。
- **重要: 原文は「human-readable なキー名」であって、同一性の実体ではない**。エントリの同一性は
  テーブル側の安定 ID（Unity Localization なら SharedTableData の KeyId 相当。どのバックエンドにも
  同等物を要求する）が持つ。原文の変更は「安定 ID を保ったキー名リネーム」に変換できるため、
  訳・メタデータを失わずに追従できる（次節）。

## 2. opt-in アセンブリ `Novel.Localization`

`Novel.Addressables` と同型の versionDefines パターン
（`com.unity.localization` 導入時のみ `NOVEL_LOCALIZATION` でコンパイル）。

- `LocalizedTableTextResolver : ITextResolver` — 指定 String Table Collection を参照する同期 resolve。
- **初期化契約**: Unity Localization のテーブルロードは async（Addressables 経由）だが
  `Resolve` は同期のため、**`PlayAsync` 前にテーブルをロード済みにする**。実装側に
  `UniTask InitializeAsync(ct)`（`LocalizationSettings.InitializationOperation` + テーブル preload）を持ち、
  game が起動時ないしノベルパート入場前に await する。未初期化中の resolve は原文フォールバック。
- ロケール切替（`SelectedLocale` 変更）は**次の resolve から反映**。表示中の行・バックログの遡及再描画は
  しない（バックログは表示時ロケールで確定）。切替 UI・フォント切替は game/View 所有。
- DI 登録は game が `ITextResolver` を差し替える 1 行（`RegisterNovelKitCore` の既定 `IdentityTextResolver`
  を上書き）。登録ヘルパの糖衣は実装時に確定。

## 3. 追従抽出パイプライン（`Novel/Localization/Extract Strings`・方式の中核）

`.rb` を静的走査して say/narration/キャラ名糖衣/choose/`as:` の文字列リテラルを抽出するが、
**blind upsert ではなく差分抽出**である。原文変更を検出してキーリネームに変換し、訳を運ぶ
（gettext `msgmerge` 系の fuzzy 機構が先例）。

構造は **2 層**: 全プロジェクト共通の**追跡エンジン**（原稿不変）と、その上の opt-in 強化層
**annotate モード**（行末 ID コメントで対応付けを決定的化）。どちらを使うかはプロジェクトの
翻訳ワークフローで決まる（後述の採用基準）。**既定はエンジンのみ**（原稿不変を既定に保つ）。

### 層 1: 追跡エンジン（基盤・原稿不変）

1. テーブルエントリに前回抽出時の**出所メタデータ**（ファイル + 出現順）を持たせる
   （独立サイドカーは持たない。追跡状態はテーブルに同居させ、コミット単位を 1 つにする）。
2. 再抽出時、ファイル単位で前回の原文列と新抽出結果を **LCS diff** し、変化行を**位置で対にする**
   （書き直された行は同じファイルのほぼ同じ位置に居る。前後の挿入・削除は LCS が吸収）。
3. 対になった変化をタグ除去後の平文の類似度（正規化編集距離）で分類する:
   - **平文一致**（タグだけの変更）→ キーリネーム・全訳保持・「タグ移植要」フラグ。
   - **高類似**（誤字修正・句読点・軽微な推敲）→ キーリネーム・全訳保持・**fuzzy**（要再確認）。
   - **低類似**（リライト）→ 旧訳をメタデータへ参考退避し**未訳化**（stale 訳を出し続けない）。
4. 対にならない消滅キーは **deprecated マーク**（削除しない）。新出は未訳の新規エントリ。
5. 適用前に**移行レポート**（新規 / リネーム(類似度%) / deprecated）を人間が確認してから書き込む。

**エンジンの構造的限界**（annotate モードの存在理由）:
- 類似度ヒューリスティックの**誤対応が原理的に残る**（連続リライト・似た行の近接）。
  レポート確認が防波堤だが、すり抜けは「誤った訳が黙って付く」形で出る。
- **ファイル跨ぎのシーン移動を追えない**（orphan 化）。
- 抽出を挟まず編集が重なると対応付けの基準が陳腐化し、**既存訳の追従精度が下がる**（鮮度管理が要る）。

### 層 2: annotate モード（opt-in・対応付けの決定的化）

対象行に短い**行末 ID コメント**を付与する（Ruby コメントはコンパイルで消えるため
`.mrb` にもランタイムにも影響ゼロ。ID は追跡専用）。

```ruby
alice "本気なの？"                 # t:a3f9
narration "——沈黙が流れた"          # t:k20x
```

- 抽出は「ID→原文」の突き合わせになり、変化の分類（上記 3）だけが残る。誤対応は構造的に消え、
  **ファイル跨ぎ移動も追従**し、ID は行に分散するので普通のテキストとしてマージされる。
  annotate を回し忘れても**既存訳は壊れない**（ID 無しの新規行が未追跡になるだけ。未訳なので実害小）。
- ID 付与・コメント消失の救済・コピペ重複 ID の振り直しには**エンジンの位置 + 類似度マッチを使う**
  （層 2 は層 1 を内包する追加層であり、置き換えではない）。
- **対価**: 原稿がツールと共有状態になる（ライター規約「`# t:xxxx` は消さない・手で書かない」が 1 つ増える）・
  annotate を回す係とタイミングの取り決めが要る（ライター/エンジニア/CI のいずれか。運用設計が必要）・
  導入時に全対象行への一括 diff が一度発生する・原稿の見た目に機械 ID が常在する。

### トレードオフと採用基準

| 観点 | エンジンのみ（原稿不変） | annotate 有効 |
|---|---|---|
| 対応付けの正しさ | ヒューリスティック（レポート確認が防波堤） | ほぼ決定的（残るのはコピペ重複の判定のみ） |
| ファイル跨ぎ再構成 | 追えない | 追える |
| 原稿への影響 | ゼロ | 行末コメント + 規約 1 つ + 導入時一括 diff |
| 運用の失敗耐性 | 抽出の鮮度が落ちると既存訳の追従を直撃 | 回し忘れは新規行の未追跡に留まる |
| 失敗の現れ方 | 訳資産の静かな劣化（気づきにくい） | ワークフローの摩擦（可視・直しやすい） |

この差が効くのは**「訳が存在する期間」と「原稿が動く期間」が重なる場合だけ**であり、選択は
プロジェクトの翻訳ワークフローが決める:

- **後追い翻訳**（原稿凍結後に翻訳開始）→ エンジンのみで十分。重なりはリリース後のプロセ修正
  パッチ程度で、レポート確認で捌ける規模。原稿を汚さない利点を取る。
- **並行翻訳**（執筆と翻訳が同時進行）・原稿再構成が頻発・訳資産が高価（外注）
  → annotate を有効化。決定性が恒常的に効き、摩擦コストを払う価値がある。

既定をエンジンのみとするのは、v1 ADR の核心「著者体験を変えない」を既定に保ち、逸脱（規約を課す）は
必要が実証されたときに opt-in する novel-kit の流儀（no-op 既定・opt-in ファセット）に合わせるため。

**2026-08-08 確定**: プロジェクト群の翻訳ワークフローは**後追い翻訳型**（原稿凍結後に翻訳開始）と
ユーザー確認。採用基準に照らし**既定 = 追跡エンジンのみで確定**。annotate モードは本 ADR の仕様の
まま保持し、並行翻訳の実需要が出た時点で実装する。

### 具体的ユースケースと挙動

| ユースケース | 例 | エンジンのみ | annotate 有効 |
|---|---|---|---|
| 誤字修正 | 「本気なの？」→「本気なの…？」 | 位置対 + 高類似 → 訳保持 + fuzzy | ID 一致で決定的に同じ結果 |
| タグ付け足し | 既存行に `<w>` を挿入 | 平文一致 → 訳保持 + タグ移植フラグ | 同左（決定的） |
| 行のリライト | セリフを別内容に書き直し | 低類似 → 旧訳退避・要再翻訳 | 同左（決定的） |
| 行の分割/結合 | 1 say → 2 say | LCS が 1↔2 置換として検出、重なり大の側に carry | ID 保持側 carry・コピー側は重複検出で振り直し |
| 行の挿入/削除 | 途中にシーン追加/削除 | LCS が位置ずれを吸収・既存行は無影響 | 同左 |
| シーンを別ファイルへ移動 | `.rb` 分割・再構成 | **追えない**（orphan → deprecated + 新規） | **ID が追従**（無影響） |
| 共有行の一方だけ変更 | 同一文が複数シナリオに出現 | 出現カウントで検知し使用中原文はリネームしない | 行ごとに別 ID で決定的に分離 |
| 連続する複数行を同時リライト | シーン丸ごと推敲 | **誤対応リスク**（レポートで人間確認） | ID 一致で決定的 |

### ランタイムキーはどちらのモードでも原文（重要な注意）

ID は**追跡専用**である。Ruby コメントは `.mrb` に焼かれず、`ITextResolver.Resolve(raw)` は raw
テキストしか受け取らないため、**ランタイムの解決キーは常に原文**。同一原文が別 ID を持つ場合、
テーブル上は 1 つの解決エントリに収斂させる（ID 群はメタデータとして保持し、一方の原文が変われば
自エントリへ分離する）。したがって「同一原文の訳し分け不可」の制約は annotate を入れても変わらない
（解消するには `tkey:` kwarg 化 = 原稿の意味的書き換えが必要。Phase 4 の検討事項のまま）。

### fuzzy のランタイム意味論

fuzzy エントリは**保持した訳をそのまま表示する**（支配的ケースは誤字修正で、その場合の旧訳は
ほぼ正しい。原文=日本語へのフォールバックは非 JP プレイヤーにとってより悪い）。dev では未確認
fuzzy の一覧をレポートし、翻訳者の確認で解除する。リライト（低類似）は fuzzy ではなく未訳扱い
なので、書き直した行に古い意味の訳が出続けることはない。

### 静的抽出の補完

糖衣の間接呼びや動的組み立てによる抽出漏れは、dev 実行時の**未ヒット収集**で回収する:
dev ビルドで resolver がテーブルミスした原文を記録し、レポート/テーブル追記できるようにする
（警告ファセットと同じ dev 支援の位置付け）。

## 4. 既読 ID のロケール不変化（先行する唯一のコア変更）

現状 `NovelCommandHandler` は **resolve 後**テキストから既読 ID（`StableId`）を算出しており、
このままでは言語を切り替えると既読/スキップが言語ごとに分断する。

- **raw（原文）から算出する**よう変更する。既定の恒等 resolver では resolved == raw のため、
  既存プロジェクトの既読ハッシュは不変（セーブ互換を壊さない無害な移行）。
- choose の結果キーは明示 StateKey で既にロケール非依存（変更不要）。

## 5. 適用範囲と非対象

| 対象 | 扱い |
|---|---|
| say 本文・話者表示名・choose 選択肢 | 実装済み seam のまま原文キーで解決 |
| 既読/スキップ | 原文基準の ID でロケール不変（上記 4） |
| バックログ | 表示時ロケールで確定・遡及再翻訳しない（受容） |
| 辞書ルビ（`IRubyDictionary`） | JP 専用スタイリング。非 JP ロケールでは game が空辞書/差し替えで無効化（resolver と独立） |
| 画像内テキスト等のローカライズ済みアセット | AssetTable ベースの `ISpriteLoader` 実装は将来オプション（バックログ） |
| voice | 対象外のまま（[音声スコープ](/design/decisions/audio-scope.md)） |
| フォント/TMP フォールバック | View/game 所有（参考 View への支援はバックログ） |

## 6. 段階導入

1. **Phase 1（コア・挙動不変）**: 既読 ID を raw 基準へ移行。
2. **Phase 2**: `Novel.Localization` アセンブリ + `LocalizedTableTextResolver` + 初期化契約。
3. **Phase 3**: 追跡エンジン（LCS + fuzzy / 移行レポート）+ dev 未ヒット収集。
   annotate モードは仕様のみ確保し、**並行翻訳の実需要が出た時点で実装**する。
4. **Phase 4（バックログ）**: 訳し分けのための文脈付き resolve オーバーロード
   （speakerId 等を渡す default interface method）・ロケール横断のタグ整合検証
   （`Novel/Validate Scenarios` 拡張）・AssetTable スプライトローダ・locale-aware ルビ・
   参考 View のフォント切替支援。
   （当初ここにあった「`#{}` 補間の救済」はテキスト変数 `%{key}` として前倒し実装済み → 実装で確定）

# 実装で確定（2026-08-08・Phase 1-3 実装）

- **Phase 1**: 既読 ID を raw 基準へ移行済み（`NovelCommandHandler`。恒等 resolver では
  `ReferenceEquals` により再計算も増えない）。`NovelLine.PlainText` は表示言語基準のまま。
- **Phase 2**: `Novel.Localization` に `LocalizedTableTextResolver(tableReference, sourceLocaleCode?)` を実装。
  `sourceLocaleCode`（例 "ja"）一致中はテーブルを引かず常に原文（原文ロケールのテーブル整備を不要にする）。
  ロケール切替は event 購読で自動追従（切替直後〜再ロード完了は原文フォールバック）。
  抽出漏れの dev 収集は resolver の `TextMissed` イベント + `MissingTextCollector` で実装。
- **Phase 3**: 追跡エンジンは仕様どおりテーブル同居メタデータ（`NovelTextSourceMetadata`＝出現ごとに 1 つ）
  + LCS + タグ除去平文の類似度分類で実装。分類しきい値は fuzzy ≥ 0.55 / 対化 ≥ 0.25（`TrackedTextDiffer` 定数）。
  fuzzy/参考退避/deprecated は Unity Localization の Shared エントリメタデータ
  （`NovelFuzzyMetadata` / `NovelArchivedTranslationMetadata` / `NovelDeprecatedMetadata`）で表現。
  純ロジック（走査/diff）は `Novel.Editor/Localization/` に置き EditMode テストを持つ。
  抽出対象は say 本文・`as:`/`display_as:`・choose 選択肢で、**say の話者 id は抽出しない**
  （カタログ id が普通。その場話者のリテラル表示名は dev 収集で回収）。
- **テキスト変数 `%{key}`（2026-08-09・「補間は対象外」の撤回）**: 当初 v1 制約として受容した
  `#{}` 問題は「変数を使うな」ではなく **遅延展開テンプレート**で解決した。`NovelTextVariables.Expand`
  が say 本文・表示名・choose 選択肢の resolve 後に `%{key}` を展開する。値は game 供給
  `ITextVariableProvider`（no-op 既定・後勝ち登録）優先で `IStateStore` の変数値へフォールバック。
  未定義はプレースホルダ温存 + dev 警告（黙って消さない）。エスケープは `%%{`。既読 ID は
  テンプレート基準なので値が変わっても既読が割れない（`#{}` に存在した既読分断も解消）。
  ローカライズ非依存の機能として Runtime に置く（`Novel.Localization` 不要で単言語でも使える）。
- 検証状況: 実装環境に Unity が無いため、EditMode テストと Unity Localization API を使う
  Editor 層は**実機（Unity + com.unity.localization 導入）での確認が未了**。

# 既知の制約（v1 として受容）

- **annotate モード導入時の一括 diff**（annotate を有効化する場合のみ）: 全対象行への ID 付与で
  一度だけ大きな機械的 diff が発生する（以後は新規行への 1 コメント追加のみ）。導入 PR として
  分離すればレビュー負担は限定的。
- **Ruby 補間 `#{}` はローカライズ不可**（Ruby が発行前に即時評価しテンプレートが C# へ届かないため。
  さらに値が変わるたび既読 ID が割れる）。ただし**変数の文中表示自体はテキスト変数 `%{key}` で一級対応**
  （2026-08-09 追記。下記「実装で確定」）: `%{key}` は Ruby で不活性の素文字列なのでテンプレートのまま
  キーになり、**訳の取得後**に `IStateStore`（`flag`/`val` 値）/ game 供給 `ITextVariableProvider`
  （主人公名等）から展開する。gettext / Rails i18n のプレースホルダ方式と同型で、翻訳者は訳文中で
  プレースホルダを自由に動かせる。ガイドラインは「変数は `%{}` で書く（`#{}` は使わない）」へ変更。
- **同一原文の訳し分け不可**（同じ「はい」が文脈で yes/okay に分かれる等）。キーが原文のみのため
  同一訳になる。頻度は低いと見込み v1 は受容し、文脈付きオーバーロードを Phase 4 で検討。
- 語順の都合で分割行（複数 say に跨るセンテンス）の翻訳が不自然になり得るのは
  行単位提示モデルの本質的制約（全ノベルエンジン共通）で、方式によらない。

# 理由

- **原文キー**: 著者体験を一切変えず、抽出・フォールバック・翻訳者の可読性（キー列に原文が見える）が
  すべて自然に成立する。`ITextResolver` シグネチャ不変で「非破壊後付け」の約束をそのまま履行できる。
- **追従抽出が方式の成立条件**: 原文キーの既知の弱点「原文を直すと訳が迷子になる」は、
  同一性を安定 ID に持たせ、変更をリネームに変換することで潰す。トレードオフの実体は
  「著者がキー管理を負う（明示キー）」vs「ツールが追跡を負う（原文キー）」であり、
  シナリオライターに負担を寄せない後者を選ぶ。gettext が同じ選択で長期運用できている。
- **2 層構造（エンジン + opt-in annotate）**: 追跡精度と原稿不変のどちらを取るかは、
  「訳が存在する期間と原稿が動く期間の重なり」というプロジェクト側の変数で決まり、ライブラリが
  一方に焼き込むべきでない。annotate はエンジンを内包する追加層なのでエンジン先行実装は捨て仕事に
  ならず、既定をエンジンのみとすることで「著者体験を変えない」を既定のまま保てる。
- **バックエンド中立 + 第一実装 Unity Localization**: コア契約（`ITextResolver`・抽出/追従・
  スナップショット）はパッケージ非依存。その上で第一実装は、既存プロジェクトに採用実績があり
  テーブル編集・翻訳ワークフロー（CSV/Sheets）・Locale 管理を再発明せずに済む Unity Localization を選ぶ。
  合わない game は同じ契約で自前テーブル実装に差し替えられる。
- **opt-in アセンブリ**: `Novel.Runtime` 純 C# と「未導入 game に無負担」を versionDefines の
  実績パターン（`Novel.Addressables`）で両立する。

# 検討した代替案

- **明示キー DSL（`say :line_001`）**: プロセ直書きの著者体験を破壊。シナリオがキーの羅列になり
  ライターが読み書きできない。[v1 ADR](/design/decisions/localization.md) で棄却済み。
- **追跡を単一モードに固定**（エンジンのみ、または annotate 常時必須）: エンジンのみ固定は
  並行翻訳プロジェクトに誤対応・orphan の恒常リスクを課し、annotate 必須は後追い翻訳プロジェクトに
  不要な規約と原稿ノイズを課す。決め手となる変数（翻訳ワークフロー）はプロジェクト側にあるため、
  どちらの固定も不採用とし 2 層 + 採用基準の形にした（本文「トレードオフと採用基準」）。
- **ロケール別 `.rb` セット**（`IScenarioSource` がロケールで選択）: 翻訳同期が手動で、分岐/フラグ/既読の
  整合リスクを翻訳者が負う。主方式にしない（構造が言語で異なる特殊シナリオの逃げ道として将来併用は可能）。
- **ハッシュキー**（原文の StableId をキーに）: テーブルが翻訳者に不可読。原文キーで足りる。
- **カタログ SO に `LocalizedString` を直接埋める**: 表示名だけ別機構になり seam が割れる。
  `ITextResolver` 一点集約を維持する。
- **`ITextResolver` を async 化**: 行ごとの await はタイプライタ開始レイテンシとコア API 破壊の割に、
  テーブル preload で同期解決できるため不要。
