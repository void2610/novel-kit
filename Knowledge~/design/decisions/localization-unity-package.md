# 状況

[ローカライズ v1 ADR](/design/decisions/localization.md) は「日本語のみ + 抽出フック」で確定し、
`ITextResolver`（既定は恒等変換）が say 本文・話者表示名・choose 選択肢に適用済み
（[API 表面](/design/api-surface.md)）。多言語は「このフックの差し替えで非破壊後付け」と約束されている。
本 ADR はその後付けの具体方策である。

前提と制約:

- **著者体験（`.rb` にプロセ直書き）は変えない**（v1 ADR の核心）。シナリオライターがキーの羅列を
  書く方式は最初から論外で、`.rb` 上のテキストは常に読める日本語プロセであること。
- 原文は書き直されるもの（誤字修正・推敲・タグ付け足し）。**原文が変わっても訳が迷子にならない
  追従機構**が方式の成立条件である。これが無い原文キーは「一度書いたら直せない」制約を著者に課す
  ことになり、v1 の核心と矛盾する。
- `Novel.Runtime` は純 C# を維持し、特定のローカライズパッケージへ直接依存しない。
  未導入の game には一切の負担を掛けない（opt-in）。
- 運用前提: **ライターの原稿はエンジニアレビュー付きの PR で取り込まれる**。原稿ファイルに
  ツールが入れる注釈は、エンジニアがレビューで意味を担保できる（2026-08-07 議論で確認）。
- 既存プロジェクト群には Unity Localization Package (`com.unity.localization`) の採用実績がある
  （Locale 管理・CSV/Google Sheets 連携等のツーリング資産）。ただしこれは**バックエンド候補の参考**で
  あって前提ではない。コア契約はバックエンド中立に設計し、Unity Localization は第一実装とする。

# 決定

方策の核は 3 点: **(a) 原文キー**（著者はプロセを書くだけ）、**(b) 追従抽出パイプライン**
（原文変更を差分検出してキーリネームに変換し訳を運ぶ）、**(c) opt-in resolver**
（`ITextResolver` 差し替え・コア API 不変）。テーブルバックエンドは中立で、
第一実装として `Novel.Localization`（Unity Localization 統合）を同梱する。

## 1. キー戦略: 原文（日本語 raw テキスト）をそのままキーにする

- `.rb` は日本語直書きのまま。String Table のキーに **resolve 前の原文**（インラインタグ込み、
  `SayCommand.Text` / `DisplayAs` / カタログ表示名 / choose 選択肢の生文字列）を使う。
- resolver は `Resolve(raw)` で raw をキーに現在ロケールのテーブルを引き、
  **ヒットしなければ raw をそのまま返す**（テーブル未整備・訳抜けでも従来挙動に落ちる健全なフォールバック）。
- 日本語ロケールはキー自体が表示文字列なのでテーブル値は不要（入れてもよい）。
- `ITextResolver` のシグネチャは不変。既存 seam をそのまま使い、コア API に変更は生じない。

```
say "本気なの？"                     # .rb は不変（著者体験そのまま）
   └ ITextResolver.Resolve("本気なの？")
        └ StringTable[ja→そのまま / en→"Are you serious?"]  ヒットしなければ原文
```

- タグ込み原文がキーになるため、**翻訳文も同じインラインタグを訳側で書く**
  （`<w>`/`<color>` 等の位置は言語ごとに移動してよい）。タグ整合の検証はバックログ（後述）。
- **重要: 原文は「human-readable なキー名」であって、同一性の実体ではない**。エントリの同一性は
  テーブル側の安定 ID（Unity Localization なら SharedTableData の KeyId 相当。どのバックエンドにも
  同等物を要求する）が持つ。原文の変更は「安定 ID を保ったキー名リネーム」に変換できるため、
  訳・メタデータを失わずに追従できる（次節）。

## 2. opt-in アセンブリ `Novel.Localization`

`Novel.Addressables` と同型の versionDefines パターン
（`com.unity.localization` 導入時のみ `NOVEL_LOCALIZATION` でコンパイル）。

- `LocalizedTableTextResolver : ITextResolver` — 指定 String Table Collection を参照する同期 resolve。
- **初期化契約**: Unity Localization のテーブルロードは async（Addressables 経由）だが
  `Resolve` は同期のため、**`PlayAsync` 前にテーブルをロード済みにする**。実装側に
  `UniTask InitializeAsync(ct)`（`LocalizationSettings.InitializationOperation` + テーブル preload）を持ち、
  game が起動時ないしノベルパート入場前に await する。未初期化中の resolve は原文フォールバック。
- ロケール切替（`SelectedLocale` 変更）は**次の resolve から反映**。表示中の行・バックログの遡及再描画は
  しない（バックログは表示時ロケールで確定）。切替 UI・フォント切替は game/View 所有。
- DI 登録は game が `ITextResolver` を差し替える 1 行（`RegisterNovelKitCore` の既定 `IdentityTextResolver`
  を上書き）。登録ヘルパの糖衣は実装時に確定。

## 3. 追従抽出パイプライン（`Novel/Localization/Extract Strings`・方式の中核）

`.rb` を静的走査して say/narration/キャラ名糖衣/choose/`as:` の文字列リテラルを抽出するが、
**blind upsert ではなく差分抽出**である。原文変更を検出してキーリネームに変換し、訳を運ぶ。
同一性の対応付けは**行末 ID コメント**で決定的に行い（xgettext がソースに位置情報を刻むのと同系）、
「意味が変わったか」の分類には gettext `msgmerge` 系の fuzzy 機構を使う。

### 同一性追跡は行末 ID コメント方式（主）

対象行に、抽出ツールが**行末 ID コメント**を付与する（短い base36 ID。形式は実装時確定）。

```ruby
alice "本気なの？"                 # t:a3f9
narration "——沈黙が流れた"          # t:k20x
```

- Ruby コメントはコンパイルで消えるため **`.mrb` にもランタイムにも一切影響しない**。
  ID は抽出側の追跡専用で、行とテーブルエントリを決定的に結ぶ。
- 当初は「ツールが原稿を書き換える」ことを理由に棄却したが、**原稿はエンジニアレビュー付き PR で
  入る運用**（前提と制約）ではこの懸念は緩和され、決定的追跡の利点が勝つと再評価した:
  - 類似度ヒューリスティックの**誤対応リスクが消える**（fuzzy 判定は「意味が変わったか」の分類にだけ残る）。
  - **ファイル跨ぎのシーン移動**も追従する（位置アンカーでは原理的に不可能）。
  - サイドカースナップショット不要 → 「抽出を挟まず編集が重なって snapshot が drift する」
    「集中ファイルがマージ衝突する」旧方式の実弱点が消える。ID コメントは行に分散し普通にマージされる。
  - PR diff 上「テキスト変更・ID 不変」= 訳が追従する行、「ID 無し」= 新規行と**レビューアに可視化**され、
    むしろレビュー可読性が上がる。
- ライター向けの規約は 1 つだけ:「`# t:xxxx` は消さない・手で書かない」（コピペで重複しても
  ツールが検出して振り直す。消えても新規扱いに落ちるだけで壊れない。PR レビューが safety net）。

### 抽出パス（`Annotate & Extract`）

1. **ID 付与**: ID 無しの対象行に新 ID を振る。このとき既存テーブルとの**位置 + 類似度マッチ**で
   既存エントリを再利用する（初回導入・コメント消失の救済。LCS はここにのみ残る）。
2. **重複 ID 検出**: コピペ由来の重複を位置ヒューリスティックで振り直し、レポートに出す。
3. **テーブル同期**: ID→原文のマップを突き合わせ、原文が変わった ID は「安定 ID 同一のまま
   キー名リネーム」とし、タグ除去後の平文の類似度で分類する:
   - **平文一致**（タグだけの変更）→ 全訳保持・「タグ移植要」フラグ。
   - **高類似**（誤字修正・句読点・軽微な推敲）→ 全訳保持・**fuzzy**（要再確認）。
   - **低類似**（リライト）→ 訳をメタデータへ参考退避し**未訳化**（stale 訳を出し続けない）。
4. 消滅した ID は **deprecated マーク**（削除しない・訳資産は消さない）。新出 ID は未訳の新規エントリ。
5. 適用前に**移行レポート**（新規 / リネーム(類似度%) / 重複振り直し / deprecated）をウィンドウ表示し、
   人間が確認してからバックエンドへ書き込む。

### 具体的ユースケースと挙動

| ユースケース | 例 | 検出 | 訳の運命 |
|---|---|---|---|
| 誤字修正 | 「本気なの？」→「本気なの…？」 | ID 不変 + 高類似 → 決定的リネーム | **保持** + fuzzy（翻訳者が確認して解除） |
| タグ付け足し | 既存行に `<w>` を挿入 | ID 不変 + 平文一致 → リネーム | **保持** + タグ移植フラグ |
| 行のリライト | セリフを別内容に書き直し | ID 不変 + 低類似 | 旧訳を参考退避・**要再翻訳**（stale 訳を出し続けない） |
| 行の分割/結合 | 1 say → 2 say（片方コピペ） | 片方が ID 保持・コピー側は重複 ID → 振り直し + レポート | 保持側 carry、新規側は未訳 |
| 行の挿入/削除 | 途中にシーン追加/削除 | 新規 ID / ID 消滅 → deprecated | 既存行は**無影響** |
| シーンを別ファイルへ移動 | `.rb` 分割・再構成 | **ID がそのまま追従**（位置追跡では不可能なケース） | 無影響 |
| 共有行の一方だけ変更 | 同一文が複数シナリオに出現 | 行ごとに別 ID なので決定的に分離 | 変更側だけ新キーへ分離（訳コピー + fuzzy）・他方は無影響 |
| コメント消失/破損 | ライターが誤って削除 | ID 無し行として位置 + 類似度マッチで救済、レポートに出す | 高確率で再接続・失敗しても新規扱い（壊れない） |

### ランタイムキーは従来どおり原文（重要な注意）

ID は**追跡専用**である。Ruby コメントは `.mrb` に焼かれず、`ITextResolver.Resolve(raw)` は raw
テキストしか受け取らないため、**ランタイムの解決キーは原文のまま**。同一原文が別 ID を持つ場合、
テーブル上は 1 つの解決エントリに収斂させる（ID 群はメタデータとして保持し、一方の原文が変われば
自エントリへ分離する）。したがって「同一原文の訳し分け不可」の制約は ID を入れても変わらない
（解消するには `tkey:` kwarg 化 = 原稿の意味的書き換えが必要。Phase 4 の検討事項のまま）。

### fuzzy のランタイム意味論

fuzzy エントリは**保持した訳をそのまま表示する**（支配的ケースは誤字修正で、その場合の旧訳は
ほぼ正しい。原文=日本語へのフォールバックは非 JP プレイヤーにとってより悪い）。dev では未確認
fuzzy の一覧をレポートし、翻訳者の確認で解除する。リライト（低類似）は fuzzy ではなく未訳扱い
なので、書き直した行に古い意味の訳が出続けることはない。

### 静的抽出の補完

糖衣の間接呼びや動的組み立てによる抽出漏れは、dev 実行時の**未ヒット収集**で回収する:
dev ビルドで resolver がテーブルミスした原文を記録し、レポート/テーブル追記できるようにする
（警告ファセットと同じ dev 支援の位置付け）。

## 4. 既読 ID のロケール不変化（先行する唯一のコア変更）

現状 `NovelCommandHandler` は **resolve 後**テキストから既読 ID（`StableId`）を算出しており、
このままでは言語を切り替えると既読/スキップが言語ごとに分断する。

- **raw（原文）から算出する**よう変更する。既定の恒等 resolver では resolved == raw のため、
  既存プロジェクトの既読ハッシュは不変（セーブ互換を壊さない無害な移行）。
- choose の結果キーは明示 StateKey で既にロケール非依存（変更不要）。

## 5. 適用範囲と非対象

| 対象 | 扱い |
|---|---|
| say 本文・話者表示名・choose 選択肢 | 実装済み seam のまま原文キーで解決 |
| 既読/スキップ | 原文基準の ID でロケール不変（上記 4） |
| バックログ | 表示時ロケールで確定・遡及再翻訳しない（受容） |
| 辞書ルビ（`IRubyDictionary`） | JP 専用スタイリング。非 JP ロケールでは game が空辞書/差し替えで無効化（resolver と独立） |
| 画像内テキスト等のローカライズ済みアセット | AssetTable ベースの `ISpriteLoader` 実装は将来オプション（バックログ） |
| voice | 対象外のまま（[音声スコープ](/design/decisions/audio-scope.md)） |
| フォント/TMP フォールバック | View/game 所有（参考 View への支援はバックログ） |

## 6. 段階導入

1. **Phase 1（コア・挙動不変）**: 既読 ID を raw 基準へ移行。
2. **Phase 2**: `Novel.Localization` アセンブリ + `LocalizedTableTextResolver` + 初期化契約。
3. **Phase 3**: 追従抽出パイプライン（スナップショット / LCS + fuzzy / 移行レポート）+ dev 未ヒット収集。
4. **Phase 4（バックログ）**: `#{}` 補間の救済（Smart String / 明示キー糖衣 `t()`）・
   訳し分けのための文脈付き resolve オーバーロード（speakerId 等を渡す default interface method）・
   ロケール横断のタグ整合検証（`Novel/Validate Scenarios` 拡張）・AssetTable スプライトローダ・
   locale-aware ルビ・参考 View のフォント切替支援。

# 既知の制約（v1 として受容）

- **導入時の一括 annotate diff**: ローカライズ開始時、全対象行への ID 付与で一度だけ大きな
  機械的 diff が発生する（以後は新規行への 1 コメント追加のみ）。導入 PR として分離すればレビュー負担は限定的。
- **`#{}` 補間入りテキスト**は実行時の最終文字列がキーになりテーブルに載らない。
  v1 ガイドラインは「ローカライズ対象のプロセに補間を使わない」（[Docs/scenario](/../Docs/scenario/index.md) へ
  実装時に明記）。救済は Phase 4。
- **同一原文の訳し分け不可**（同じ「はい」が文脈で yes/okay に分かれる等）。キーが原文のみのため
  同一訳になる。頻度は低いと見込み v1 は受容し、文脈付きオーバーロードを Phase 4 で検討。
- 語順の都合で分割行（複数 say に跨るセンテンス）の翻訳が不自然になり得るのは
  行単位提示モデルの本質的制約（全ノベルエンジン共通）で、方式によらない。

# 理由

- **原文キー**: 著者体験を一切変えず、抽出・フォールバック・翻訳者の可読性（キー列に原文が見える）が
  すべて自然に成立する。`ITextResolver` シグネチャ不変で「非破壊後付け」の約束をそのまま履行できる。
- **追従抽出が方式の成立条件**: 原文キーの既知の弱点「原文を直すと訳が迷子になる」は、
  同一性を安定 ID に持たせ、変更をリネームに変換することで潰す。トレードオフの実体は
  「著者がキー管理を負う（明示キー）」vs「ツールが追跡を負う（原文キー）」であり、
  シナリオライターに負担を寄せない後者を選ぶ。gettext が同じ選択で長期運用できている。
- **ID コメント方式の採用**: 追跡を決定的にする対価は「原稿に短い行末コメントが付く」ことだが、
  原稿がエンジニアレビュー付き PR で入る運用ではレビューアが担保でき、diff 上で訳の追従有無が
  可視化される利点が上回る。誤対応ゼロ・ファイル跨ぎ移動対応・サイドカー不要（drift/マージ衝突の
  排除）を同時に得る。
- **バックエンド中立 + 第一実装 Unity Localization**: コア契約（`ITextResolver`・抽出/追従・
  スナップショット）はパッケージ非依存。その上で第一実装は、既存プロジェクトに採用実績があり
  テーブル編集・翻訳ワークフロー（CSV/Sheets）・Locale 管理を再発明せずに済む Unity Localization を選ぶ。
  合わない game は同じ契約で自前テーブル実装に差し替えられる。
- **opt-in アセンブリ**: `Novel.Runtime` 純 C# と「未導入 game に無負担」を versionDefines の
  実績パターン（`Novel.Addressables`）で両立する。

# 検討した代替案

- **明示キー DSL（`say :line_001`）**: プロセ直書きの著者体験を破壊。シナリオがキーの羅列になり
  ライターが読み書きできない。[v1 ADR](/design/decisions/localization.md) で棄却済み。
- **サイドカースナップショット + 位置アンカー LCS のみで追跡**（ID コメント無し・原稿完全不変）:
  当初案。原稿を一切書き換えない利点はあるが、(1) 類似度ヒューリスティックの誤対応が残る
  (2) ファイル跨ぎのシーン移動を追えない (3) 集中サイドカーの drift・マージ衝突という運用弱点を持つ。
  「原稿はエンジニアレビュー付き PR で入る」前提の確認（2026-08-07）により ID コメントの懸念
  （著者に謎コメントを見せる）が緩和されたため、主方式を ID コメントへ変更し、本案は
  ID 付与時の初回マッチ/コメント消失時の救済として内部に残す。
- **ロケール別 `.rb` セット**（`IScenarioSource` がロケールで選択）: 翻訳同期が手動で、分岐/フラグ/既読の
  整合リスクを翻訳者が負う。主方式にしない（構造が言語で異なる特殊シナリオの逃げ道として将来併用は可能）。
- **ハッシュキー**（原文の StableId をキーに）: テーブルが翻訳者に不可読。原文キーで足りる。
- **カタログ SO に `LocalizedString` を直接埋める**: 表示名だけ別機構になり seam が割れる。
  `ITextResolver` 一点集約を維持する。
- **`ITextResolver` を async 化**: 行ごとの await はタイプライタ開始レイテンシとコア API 破壊の割に、
  テーブル preload で同期解決できるため不要。
